# SQLite history proof

This is an inert, temporary-directory-only candidate, not an approved persisted production format. Nothing mounts it. The caller must exclusively control the owner-only temporary subdirectory and database; concurrent file replacement or external writers are not supported. Admission rejects sidecars and validates existing files using immutable read-only SQLite before a writable open. Unclean databases with sidecars are rejected, not recovered. Create uses exclusive file creation; failed creation can leave an empty or incomplete file, which is never automatically removed or reinitialized. Existing files must match the candidate identity and exact schema. No migration, retention, deletion, or eviction is implemented.

Only explicitly supplied synthetic known integer memory/count gauges in the range 0 through 2^53-1 are stored. Receipt time is a Brine observation time, not a source sample time. No outage zeros are generated. One record is inserted per transaction. SQLite's default rollback journal and synchronous settings apply. Synthetic tests observe an acknowledged append survive abrupt child exit after commit and prior records survive a page-cap-induced SQLITE_FULL. This is not power-loss, mid-transaction crash recovery, or filesystem ENOSPC qualification. A successful commit is not a guarantee against faulty storage hardware.

The SQLite v1.62.0 dependency raises the module-wide x/sys selection from v0.42.0 to v0.49.0 via MVS. CGO-disabled Linux amd64 and arm64 test binaries were compile-checked, not executed. Full product packaging, license obligations, advisories, concurrent access, filesystem contention and peak main/journal/WAL/SHM footprint remain unvalidated. No total storage bound exists.
